# odata-testgen

Generates **OData regression tests** from service metadata, so every service starts with
baseline coverage of its API contract and authorization.

| Output | For | Runs with |
|--------|-----|-----------|
| `node-test` | CAP projects | `node --test` + `cds.test` (in-process, in-memory database) |
| `postman` | any deployed OData service: RAP, S/4HANA, CAP on BTP | Postman or Newman (CI) |

## What is generated (per entity set, as far as the API allows)

- anonymous request -> **401**; user without read role -> **403**
- read collection with `$top` and `$count`; `$filter` and `$orderby`
- create -> **201** and read back; for **draft** entities the full protocol: draft, activate,
  edit, change, re-activate
- missing mandatory fields -> **400** (for draft entities: on activation)
- invalid value for a typed property -> **400**
- user without write role -> **403** on create
- update and delete (with the correct `If-Match` on ETag entities)
- **ETag**: update with a stale ETag -> **412**
- bound and unbound actions/functions: smoke call (no 401/403/404/5xx) for an allowed user,
  **403** for a denied user, **401** anonymous

Cases are planned from capabilities (`@readonly`, `@insertonly`, `@cds.autoexposed` sets are
skipped for writes) and from the authorization model.

## CAP projects

```sh
npx odata-testgen --input . --emit node-test          # writes test/generated/*.test.js
node --test "test/generated/*.test.js"                # or include them in npm test
```

Users and permissions are **derived automatically**: `@requires` / `@restrict` on services,
entities and actions, and the mocked users configured in `cds.requires.auth.users` (merged with
CAP's defaults). The generator picks an allowed and a denied user for each case and prints them:

```
SalesOrdersService (/odata/v4/sales-orders): 2 entity set(s), 0 unbound operation(s)
  SalesOrders - read: alice, write: alice, denied read: carol, denied write: bob
```

Verified: on the generated reference app all 22 generated tests pass; on a fixture with draft,
ETag, insert-only, read-only and operations all 32 pass (both run in CI-equivalent package tests).

## Deployed services (RAP, S/4HANA, CAP on BTP)

```sh
curl -u user:pass "https://host/sap/opu/odata4/sap/zui_sd_order_o4/srvd/sap/zui_sd_order/0001/\$metadata" -o metadata.xml
npx odata-testgen --input metadata.xml --emit postman \
  --base-path /sap/opu/odata4/sap/zui_sd_order_o4/srvd/sap/zui_sd_order/0001 \
  --roles roles.yaml --out tests/zsd-order.postman_collection.json
npx newman run tests/zsd-order.postman_collection.json \
  --env-var baseUrl=https://host \
  --env-var user_admin=$ADMIN_USER --env-var password_admin=$ADMIN_PASSWORD \
  --reporters cli,junit --reporter-junit-export reports/api-tests.xml
```

`roles.yaml` describes test users (credentials are passed as variables, never stored):

```yaml
users:
  admin:  { roles: [Admin] }
  viewer: { roles: [Viewer] }
requires: authenticated-user            # service level: any | authenticated-user | [Role]
permissions:
  A_SalesOrder: { read: [Viewer, Admin], write: [Admin] }
  A_SalesOrder/cancel: [Admin]           # bound operation; unbound: just the name
```

Verified with Newman against a running CAP app: 30 requests, 30 assertions, 0 failures.

## Regeneration rules

- Generated files carry `GENERATED by odata-testgen` and a What/Why/If-missing header. **Do not
  edit them** - regenerate after model changes (same input gives identical files).
- Stale generated files (e.g. of a removed entity set) are deleted; files without the marker are
  never touched.
- Put business scenarios (pricing, credit block, partner determination, ...) in hand-written
  tests, e.g. `test/scenarios/`.

## CLI

| Option | Use |
|--------|-----|
| `--input <path>` | CAP project folder, EDMX file or snapshot JSON |
| `--emit node-test\|postman` | output format |
| `--out <path>` | folder (node-test, default `<project>/test/generated`) or file (postman) |
| `--roles <file>` | users and permissions (EDMX inputs; overrides CAP derivation) |
| `--service <name>` | only one service |
| `--base-path <path>` | URL path of the service (EDMX inputs) |
| `--exclude <set>` | skip an entity set (repeatable) |

Exit codes: `0` generated, `2` usage or input error.

## Limits

- The smoke tests for operations prove reachability and authorization, not business results.
- `@restrict` `where` conditions (instance-based authorization) are not evaluated; tests use
  role grants only.
- Sample values are generic (`T1`, `1`, `2026-01-01`); handlers with stricter validation may
  reject them - exclude the set or add scenario tests.
- For V2 services, function imports are called like actions (see `sap-metadata` limits).
