# create-cap-app

Generates a CAP (Node.js) project on the organisation golden path. SAP's own scaffolding
(`cds init` / `cds add` from `@sap/cds-dk`) creates the base; an overlay adds the organisation
standards on top. Generated code is plain CAP - it does not depend on this generator at runtime.

## Usage

```sh
npx create-cap-app sales-orders                       # defaults: acme.sales, SalesOrders, HANA, CF
npx create-cap-app billing --entity Invoices --namespace acme.billing --db postgres
npx create-cap-app sales-orders --sapdx-source ~/Projects/sap-dev-accelerators   # use local tool packages
```

Exit codes: `0` generated, `1` generation failed (partial output is removed), `2` usage error or
target folder not empty (nothing is touched).

## What you get

| Area | Content |
|------|---------|
| Model / service | `db/schema.cds` (cuid, managed, composition), `srv/<name>-service.cds` with `@requires` + `@restrict` (Viewer/Admin), handler with validation and a bound `cancel` action |
| Security | `xs-security.json` scopes and role templates **derived from the model** (`cds compile --to xsuaa`), mocked users `alice` (Admin) / `bob` (Viewer) for dev/test only |
| Operations | CAP `/health` + generated `/ready` (database check), `traceparent` -> `x-correlation-id` bridging; CAP masks credential headers in JSON logs |
| Tests | `node:test` + `cds.test`: 401/403 cases, CRUD, validation, action, probes, correlation; 80 % coverage threshold |
| Gates | `npm run check` = ESLint + tests + `cap-policy-lint` (fails on new Blocker/Critical) |
| CI | GitHub Actions: lint, tests, policy SARIF -> code scanning, gitleaks, npm audit, `mbt build` |
| Docs | README, `docs/api.md`, `docs/architecture.md`, ADR 0001, `docs/files.md`, `catalog-info.yaml` |
| Deployment | `mta.yaml` with XSUAA, HANA/Postgres, destination and application logging services |

Every file starts with a *What / Why / If missing* header. The generator refuses to finish if
`cds-dk` produces a file that has no entry in `src/catalog.js`, so headers cannot silently go
missing after an SAP tooling upgrade. `xs-security.json` cannot carry a comment safely and is
documented in `docs/files.md` instead.

## Verified

- Generated project: `npm install`, `npm run check` (lint, 15/15 tests, policy gate with zero
  findings) and `mbt build` producing a deployable `.mtar` - run under Node 24.
- `reference-apps/sales-orders` is a committed generator output; CI regenerates it, diffs it and
  runs its `npm run check`.

## Design decisions

- **Node 24 LTS** (`engines: ^24`): the HANA deployer generated by CAP 10 `cds build` requires
  Node 24 and SAP runtime libraries support even LTS lines only. The Cloud Foundry buildpack picks
  the Node version from `engines`, so an open range could select an unsupported runtime.
- **Wrap, don't copy, SAP scaffolding**: SAP keeps ownership of `mta.yaml`, ESLint config etc.;
  the overlay only adds organisation content.
- **Real paths**: `file:` references are computed from resolved paths because npm resolves them
  from the real project location (macOS `/tmp` is a symlink).

## Not yet supported

- `--target kyma`: `cds add kyma` could not be verified in this toolchain (Helm not installed).
- `--tenancy multi`: the MTX sidecar is not yet covered by the generated tests.
- An actual `cf deploy` was not run (no BTP subaccount in the build environment).
