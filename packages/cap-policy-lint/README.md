# cap-policy-lint

Clean-core, security and quality checks for **CAP (Node.js)** projects against the central
[`policy/`](../../policy). It parses the CDS model (via `@sap/cds` of the analysed project or its
own copy), the server JavaScript (AST, never executed) and the configuration, and fails on new
Blocker/Critical findings.

## Rules

| Rule | Severity | Triggered by | Fix |
|------|----------|--------------|-----|
| `CAP-AUTH-001` | Critical | a service without `@requires` / `@restrict` | add `@requires: 'Role'` or `@restrict`; `@requires: 'any'` only with an exemption |
| `CAP-AUTH-002` | Critical | a writable entity not covered by `@restrict`, a business role in `@requires` (pseudo roles `any`, `authenticated-user`, `system-user`, `internal-user` do not count) or `@readonly` | restrict per event, e.g. `@restrict: [{ grant: 'READ', to: 'Viewer' }, { grant: '*', to: 'Admin' }]` |
| `CAP-SEC-001` | Blocker, not baselineable | credential keys (`password`, `secret`, `clientsecret`, `apikey`, `token`, `private_key`, ...) with literal values in JSON/YAML files and in JavaScript outside `test/` folders (placeholders such as `${...}`, `<...>`, `env:...`, `changeme` are ignored); private keys, JWTs and AWS keys in any text file (`.js`, `.json`, `.yaml`, `.cds`, `.env`, `.properties`, `.xml`, `.txt`) | remove, rotate, use service bindings / destinations / credential store |
| `CAP-CFG-001` | Major | `http(s)://` literals in `srv/` code (localhost and schema URIs allowed) | `cds.requires` + destination |
| `CAP-CFG-002` | Major | literal company code, plant, sales organisation, distribution channel, division (`bukrs`, `werks`, `vkorg`, ...) in `srv/` code | configuration or master data |
| `CAP-REMOTE-001` | Major | `cds.requires` remote service (`odata`, `odata-v2/-v4`, `rest`, `hcql`) without `credentials.destination` in production | `"[production]": { "credentials": { "destination": "S4_API" } }` |
| `CAP-PERF-001` | Major | `SELECT.from(...)` in `srv/` without `.where`, `.limit`, `.one` or `byKey` | bound the query |
| `CAP-TEST-001` | Major | an action/function whose name appears in no test file | add a test that calls it |
| `CAP-TEST-002` | Major | no test asserts `401` or `403` | add a negative authorization test |
| `CAP-LOG-001` | Minor | `console.*` in `srv/` | `cds.log('component')` |
| `CAP-API-001` | Minor | `catalog-info.yaml` missing or without `spec.owner`, `spec.lifecycle`, `metadata.annotations["sapdx.io/api-version"]` (semver) | add the ownership metadata |
| `CAP-NAME-001` | Minor | namespace, service, entity or element names not matching [`policy/naming.yaml`](../../policy/naming.yaml) | rename |

Severities are decided by [`policy/rules.yaml`](../../policy/rules.yaml), not by the linter.

## Usage

```sh
npx cap-policy-lint                                   # current folder, text report
npx cap-policy-lint path/to/project
npx cap-policy-lint . --format sarif --out reports/cap-policy.sarif
npx cap-policy-lint . --baseline cap-baseline.json    # brownfield: only new findings gate
npx cap-policy-lint . --policy ../governance/policy   # a policy folder other than ./policy
```

Text output (from the `test/fixtures/bad` project):

```
BLOCKER  CAP-SEC-001        srv/admin.js:10  Hard-coded secret in "clientSecret"; use service bindings, destinations or the credential store.
CRITICAL CAP-AUTH-001       srv/admin.cds:7  Service AdminService declares neither @requires nor @restrict.
MAJOR    CAP-TEST-002       bad-app  No test asserts an unauthorized (401) or forbidden (403) response.
...
24 finding(s): 3 blocker, 4 critical, 11 major, 6 minor

GATE FAILED: 7 new Blocker/Critical finding(s)
```

Exit codes: `0` gate passed, `1` new Blocker/Critical findings, `2` usage or configuration error.

Projects generated by [`create-cap-app`](../create-cap-app) already contain the scripts:
`npm run policy` (text) and `npm run policy:sarif` (SARIF for CI); `npm run check` runs lint,
tests and the policy gate.

## Existing projects (baseline)

```sh
npx cap-policy-lint . --format sarif --out cap.sarif
npx sapdx-gate cap.sarif --write-baseline cap-baseline.json   # commit this file
npx cap-policy-lint . --baseline cap-baseline.json            # in CI from now on
```

Only findings that are new compared with the baseline block. `CAP-SEC-001` can never be
baselined. Plan the baseline down - resolved findings are counted in every run.

## Accepting a finding (exemption)

Comments in code do not suppress anything. Add a time-boxed entry to
[`policy/exemptions.yaml`](../../policy/exemptions.yaml) - owner, approver (architect, not the
owner), justification, expiry within 12 months, backlog item - matched by `object` (e.g.
`SalesOrdersService`) or `path` glob. Expired exemptions raise `POL-EXEMPT-001` (Blocker).

## CI

```yaml
- run: npx --no-install cap-policy-lint . --format sarif --out cap.sarif
- uses: github/codeql-action/upload-sarif@v3
  if: always()
  with: { sarif_file: cap.sarif, category: cap-policy }
```

The SARIF also feeds [`sapdx-gate`](../policy) and the release-readiness check
([`sapdx-readiness`](../readiness), `RDY-FINDINGS`).

## Limits

- Static analysis: dynamic queries built from strings, or URLs assembled at runtime, are not seen.
- `CAP-TEST-001/002` check that tests *mention* the operation or status code, not that they pass;
  test results are judged by the readiness checker (`RDY-TESTS`).
- UI code under `app/` is not linted here (use UI5 linter / ESLint for UI5).
